## Where the data comes from

Fair first question, so it's answered first.

The dataset is **synthetic and generated by a script in this repo** — no real patient
records, which is the normal constraint for showing this work outside a client
engagement. It models a **donor screening laboratory**: the assay panel is the marker
set mandated for allogeneic donation screening under **EU Directive 2002/98/EC** (NAT
and serology for HIV, HBV, HCV, plus syphilis and anti-HBc), carrying real LOINC codes.

It is shaped like what a fifteen-year-old system actually hands over — pipe-delimited
flat files, Latin-1, local wall-clock timestamps with no offset column, numeric results
as free text, and a control-total manifest.

**Deterministic from a seed:** same seed, same 15,839 rows, same SHA-256 checksums. The
dataset the evidence came from can be regenerated exactly.

## Why donor screening

The assay result decides whether a unit of blood is **released for transfusion or
destroyed**. That single fact sets test depth for every field — the risk argument rests
on consequence, not opinion.

## Nine defects, injected on purpose

A pack where everything passes has proved nothing. The migration code never sees the
injection log; detection is attributed afterwards from which control fired, so it can't
be tuned to the answer.

| | Defect | Injected | Contained |
|---|---|--:|:--:|
| `DEF-01` | Assay codes with no target equivalent | 1,689 | ✅ |
| `DEF-02` | Haemoglobin `g/dL` where target expects `g/L` | 1,204 | ✅ |
| `DEF-03` | Censored `<0.10`, padded, comma decimals | 1,271 | ✅ |
| `DEF-04` | Donor names double-encoded at rest | 6 | ✅ |
| `DEF-05` | Timestamps inside the DST fallback hour | 5 | ✅ |
| `DEF-06` | Duplicate donation identifiers | 4 | ✅ |
| `DEF-07` | Results referencing absent donations | 6 | ✅ |
| `DEF-08` | Undocumented sentinel `9999` | 105 | ✅ |
| `DEF-09` | Manifest total disagrees with the file | 1 | ✅ |

**9/9 contained.** 99.3% caught by their own control; the remainder by an earlier one.

> **DEF-04 is the one worth seeing.** Byte `e1` isn't valid UTF-8, so the *clean* row
> displays as `Ferr�ndez` and looks broken. The pair `c3 ad` *is* valid UTF-8, so the
> *corrupt* row displays as `Vílchez` and looks perfect. Invisible to the eye, provable
> at the byte level — which is why this is verified on bytes and counts, not by
> eyeballing a sample.

## Reproduce

```bash
python -m venv .venv && .venv/Scripts/pip install -r requirements.txt
cd src
python -m legacy_sim.generate_extract --out ../data/legacy --oracle ../data/_oracle
python -m migration.pipeline          --extract ../data/legacy --out ../data/target
python -m reconciliation.known_answer --oracle ../data/_oracle --target ../data/target
python -m evidence.build_rtm
cd .. && .venv/Scripts/python -m pytest tests/ -q
```

AWS steps are optional and separate — see [`infra/provision/`](infra/provision/).

<sub>Synthetic data throughout. Account identifiers in published evidence are redacted;
no verdict or timestamp altered.</sub>
